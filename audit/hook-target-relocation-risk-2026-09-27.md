# Hook target absolute-address and relocation audit

Date: 2026-09-27

## Why exact-byte equality is not enough

The supplemental hook sources are byte-exact reconstructions of bounded code
from `ImVehFt.asi`; they are not yet relocatable replacements. The original
ASI is an x86 PE with preferred image base `0x10000000`, image range
`0x10000000..0x10042fff`, and entry point `0x100111b3` (confirmed with
MSVC 2022 `dumpbin /headers`). Its relevant sections include `.text` at
`0x10001000`, `.rdata` at `0x10022000`, and `.data` at `0x10029000`.

The bounded Ghidra listing in
[`asi-hook-target-cfg-2026-09-27.csv`](asi-hook-target-cfg-2026-09-27.csv)
contains 337 instruction rows for the 12 supplemental destinations. A scan of
their decoded operand strings found 181 references in the `0x100xxxxx` image
range, 79 unique addresses. Of these, 42 references (28 unique addresses) are
control-flow destinations inside one of the recovered target spans. The other
139 references (51 unique addresses) leave those spans: five are calls to
other original-ASI code addresses, 16 are `.rdata` addresses, and 30 are
`.data` addresses. The latter include mode tables, callback state, and globals
such as `0x1003c1f0` and `0x1003c258`.

This inventory is reproducible from the CSV using PowerShell by extracting
`0x100...` operands from the `mnemonic` column and comparing each value to the
per-target instruction spans. The counts describe textual decoded operands;
they are not a complete relocation table for the entire 705-function set.

The repeatable inventory in
[`hook-shim-external-reference-inventory-2026-09-27.csv`](hook-shim-external-reference-inventory-2026-09-27.csv),
generated by [`scripts/audit-hook-shim-external-refs.py`](../scripts/audit-hook-shim-external-refs.py),
reclassifies the 51 unique out-of-span image addresses: five are exact entries
in the 705 candidate map, 30 are mutable `.data` addresses, and 16 are
`.rdata` addresses. Seventeen of the 30 mutable addresses also have a
`DAT_...`/`UNK_...` identifier used in candidate sources; the other 13 have no
such identifier in the 705 source set. A matching identifier is only a naming
cross-reference, not proof that the symbol is defined at the original VA or
that it is correctly wired by a future linker. The bounded recovery
pseudocode artifacts show address-derived Ghidra aliases for 24 of the 30
mutable locations; the remaining six do not appear in those selected
decompilations. A follow-up queried the existing `ImVehFt.asi` Ghidra project
with `-readOnly -noanalysis`: all 51 addresses resolve to a memory block, have
a symbol label, and have at least one incoming reference. The sections are
`.text` (5), `.rdata` (16), and `.data` (30). The 30 data labels are default
address labels rather than semantic names; the xrefs identify concrete
read/write sites. This establishes a traceable original-image address map for
these bounded hooks, but does not supply relocated definitions for a new DLL.
See [`hook-shim-ghidra-symbol-xrefs-2026-09-27.csv`](hook-shim-ghidra-symbol-xrefs-2026-09-27.csv)
and [`scripts/GhidraReadOnlyAddressSymbols.java`](../scripts/GhidraReadOnlyAddressSymbols.java)
for the reproducible read-only query. Although the program was processed with
`-readOnly -noanalysis` and its database segment files retained their prior
timestamps, Ghidra refreshed the project index files' timestamps on open/close;
those index files are not part of the ImVehFt analysis database contents.

## Consequence for a rebuilt module

The supplemental `.asm` uses literal `DB` bytes to preserve the original
instruction stream. The COFF verifier intentionally requires no code-section
relocations, and the fresh build in `build/hook-shims/` again passes all 12
targets (1,449/1,449 bytes). That is appropriate for byte comparison, but it
also means the embedded absolute operands are not fixed up by the linker or
Windows loader. Linking these objects into a normal DLL at a new image layout
would leave references pointing into the old ASI address space. Similarly,
the original installer writes fixed `rel32` values for some hook calls, which
target the old ASI virtual addresses.

Before any runtime test, one of these must be implemented and independently
validated:

1. Reconstruct a compatible fixed-address image layout for every referenced
   code/data address, including collision/loader constraints; or
2. Convert absolute references in the 705 candidate set and supplemental
   hook bodies to relocatable symbols, and have the installer calculate each
   branch displacement from the actual loaded replacement address.

The second option is generally safer for a newly linked DLL, but it is a
substantial source/build transformation and needs whole-image relocation,
import, and hook-site tests before it can be considered valid. Neither option
has been implemented. Do not load the diagnostic DLL or these shim objects
into the game.

## Current evidence and limits

- `dumpbin /headers` confirms the original ASI image base and section ranges.
- `scripts/build-hook-shims.ps1` freshly rebuilt both supplemental objects;
  `scripts/verify-hook-shim-bytes.py` passed all 12 streams exactly.
- `audit/game-executable-hook-compat-2026-09-27.md` documents hook sites,
  fixed installer displacements, and unresolved runtime behavior.
- This audit does not claim that the 705 translation units or 12 hook bodies
  form a complete, relocatable, loadable, or behaviorally equivalent plugin.
