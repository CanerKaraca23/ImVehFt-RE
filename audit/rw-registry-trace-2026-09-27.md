# RenderWare callback registry trace

Date: 2026-09-27. Targets: local `gta_sa.exe`, the exact ImVehFt binary, and installed `ProperShaders.asi`. Evidence combines selected Ghidra 12.1.3 `-noanalysis` CFG decompilations with full auto-analysis for xrefs. Decompiled code is not original source.

## Findings

- `0x7F3BB0`, `0x7FB0B0`, and `0x7F1260` are registration wrappers. Each forwards one registry head (`0x8E23CC`, `0x8E2518`, or `0x8E2270`) and five callback/configuration arguments to `0x8084A0`.
- `0x8084A0` maintains the registry list and creates a record holding supplied callbacks. The decompilation shows callback fields in record offsets `+0x0C` through `+0x28`; the linked-list next pointer is at `+0x34`.
- `0x808740` walks records from `param+0x14`, invokes the callback at record `+0x24`, and advances using `+0x34`. This confirms the `CALL [ESI+0x24]` is registry-dispatched callback code, not an arbitrary unresolved virtual call.
- **Correction to the earlier search claim:** ImVehFt does contain a registration sequence, but it loads `0x7F3BB0` into `EAX` and calls `EAX`, so a search for direct call xrefs or named calls in the candidate sources missed it. The instruction sequence at `0x10001879..0x1000187E` calls `RwTextureRegisterPlugin(0x10, 'MEXT', 0x10001AD0, 0x10001B00, 0x10001B30)`. Bounded Ghidra decompilation from `0x10001863` confirms those arguments. The callbacks correspond to existing candidate TUs: constructor `10001ad0`, destructor `10001b00`, and copy callback `10001b30`.
- The address `0x10001863` is an interior instruction in the code sequence beginning at `0x10001850`, not a valid function-entry seed. Thus the earlier “no containing function / no route” conclusion from checking `0x10001863` as a function entry was invalid. The binary sequence at `0x10001850` checks the `SA::Render` event, logs `Attaching texture maps plugin...`, calls `RwTextureRegisterPlugin` indirectly through `EAX` at `0x1000187E` with callbacks `0x10001AD0/0x10001B00/0x10001B30`, then logs `Finished (%d).` using the registration return value. The installed `.ImVehFt/ImVehFt.log` contains those exact messages and `Finished (96).`; its filesystem timestamp is **2026-09-11 20:42:40**, not the 2026-09-27 session. This is strong historical evidence that the registration path executed and returned plugin offset 96 in at least that earlier run. The log is not proof of execution in the latest game session, nor of the current live registry contents. Static entrypoint/xref inspection remains incomplete because the actual entry starts at `0x10001850`; trace its registration/dispatch path from that correct boundary rather than treating the interior address as an orphan.
- DllMain (`0x10001DB0`) on process attach calls dispatcher `0x1000A560` with `ECX=0x0F` and `EAX=0x10001850`. The dispatcher is `JMP [ECX*4+0x1000A618]`; table slot 15 targets `0x1000A5C9`, a wrapper that forwards the callback to `0x1000B4E0`, which appends it to the internal callback array. Therefore the binary does provide an explicit route from DllMain to the registration sequence; the historical log corroborates that the sequence ran in that earlier session. Current/latest-session execution and live registry contents remain unverified.
- If the destructor callback is invoked, candidate `10001b00` calls `RwTextureDestroy` (`0x7F3820`) for its non-null nested texture pointer. That can recursively dispatch texture registry callbacks. The callback itself has no direct write to `DAT_1003C1FC`, but recursive/external callback paths have not been dynamically exercised.
- Full-analysis xrefs in the installed GTA executable found five calls to the game's three registration wrappers, with callbacks in GTA code. This does not enumerate other loaded modules or establish the live registry contents.
- A targeted Ghidra check of the installed `ProperShaders.asi` also found an indirect call to `0x7F3BB0`: plugin ID `0x0BAD1DEA`, size `4`, constructor `0x1008B680`, null destructor/copy. The constructor only zeroes its plugin slot. Its registration routine `0x100857F0` is a vtable entry at `+8` in the table rooted at `0x1017A0DC`; bounded code also constructs a stack object using that vtable. The route that dispatches this exact slot and its connection to module startup have not been traced, so this is registration code present, not proof it executes. A quick scan of active-location ASI files found additional occurrences in SkyGfx/other plugins; their call and initialization paths remain unverified.
